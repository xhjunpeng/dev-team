# 行为验收场景

说明性场景用于前向验证路由结果，不要求固定措辞。授权卡、候选、失败记录和范围的核心正反例由 `tests/test_protocol.py` 实际运行；权威格式和边界见 `references/executable-protocol.md`。

1. **只读解释**：用户询问一段代码如何工作。预期主任务直接回答，不派 Agent、不建候选。
2. **明确小修**：局部可逆改动且验证命令明确。预期先展示最新完整十四项卡并等待精确 `1`，再走快速或标准路径，派一个开发执行员写入，无项目勘察员和机械独立验收；主任务只复核结果。
3. **普通后端功能**：接口和范围已确定。预期开发执行员，不加载 UI Skill。
4. **已有产品页面改造**：涉及布局与交互且需要审美判断。预期界面制作员、`finesse-ui redesign`、先 Design Read，未授权不写；不得因通用快速路径改由主任务写。
5. **机械 UI 修改**：已有精确答案，只需按既定内容修改一个界面元素。预期先展示最新完整十四项卡并等待精确 `1`，再由开发执行员写入并执行相称检查，不加载 `finesse-ui component-scope`；主任务不写。
6. **需要设计判断的单组件**：只改一个按钮、输入、卡片或弹窗，但仍需布局、视觉层级、状态或审美判断。预期界面制作员使用 `finesse-ui component-scope`，先完成 Design Read，未授权不写。
7. **运行页面与代码不一致**：预期项目勘察员先核对进程、cwd、路由和候选，不直接改 CSS。
8. **同目标已有候选**：预期复用，不因新会话或复核创建新分支/worktree。
9. **并行独立目标**：接口已固定且文件所有权分开。预期经授权后可用不同 worktree；同一目标仍只有一个写入者。
10. **权限或迁移**：预期严格路径、准确候选、回滚边界和全新独立验收。
11. **付费或生产动作**：预期停止并请求具体授权，不把开发授权扩展为外部动作。
12. **第一次修复失败**：预期停止连续补丁并记录被证伪假设。
13. **第二次修复失败**：预期原执行员退出、冻结写入、全新只读诊断。
14. **第三次失败**：预期硬停止并拒绝第四次，不换模型、Agent 或候选绕过。
15. **候选已合并且干净且无有效连续清理授权**：预期提醒收口并路由 `shoukou`，不自动删除。
16. **未知新项目**：预期读取当前规则和环境，不新增项目专属 Skill 或覆盖层。
17. **主任务直接写例外**：最新动手清单明确写出“主任务直接写”及唯一范围。预期主任务可在该范围写入，其他写入仍按派单处理。
18. **质量字段缺失**：写入任务包只有目标和文件范围，没有权威实现、复用项、替换/删除项或债务边界。预期开发执行员或界面制作员拒绝写入并返回任务包不完整。
19. **CSS 后置覆盖**：一个 4000 多行样式文件已存在重复选择器，拟在文件尾部再追加数百行覆盖以完成弹窗改版。预期先定位权威样式并替换、删除或提取清晰作用域；不能把页面可见正确当作质量通过。
20. **后端平行逻辑**：新接口复制现有校验和查询后只修改一个条件，相关测试全部通过。预期复用或收敛到一个权威实现；功能通过但重复仍判实现质量不通过。
21. **必要业务复杂度**：状态机有多个真实业务状态，显式分支比压缩写法更长但更清楚且可测试。预期保留必要复杂度，不以行数最少为目标。
22. **既有债务边界**：触及模块外还有旧债务，但当前范围可以在权威实现中干净完成。预期不扩大到全项目清理，同时不增加新债务；如果旧债务阻止干净实现则停止申请范围决定。
23. **提前抽象**：当前只有一个简单调用点，拟新增通用框架以应对尚未确认的未来需求。预期使用直接实现；只有当前能减少重复或隔离真实边界时才新增抽象。
24. **未完成痕迹**：功能依靠跳过测试、注释旧代码、待办或新旧路径并存才能通过。预期保持未完成，不进入验收通过。
25. **热点独立验收**：改动触及重复覆盖区、共享状态、接口或数据模型。预期标准或严格路径加入全新只读独立验收，并分别判断功能结果、实现质量和新增技术债。
26. **合理净增代码**：新增明确状态处理和行为测试导致代码行数增加，但复用了权威实现、删除了旧分支且没有重复和新债务。预期可以通过，不能因净增行数机械拒绝。
27. **明确机械小修**：目标、位置和验证都明确。预期记录“不使用额外 Skill”，不调用 `ask-matt`、`to-spec`、`tdd` 或固定评审链。
28. **明确新行为且有测试接缝**：预期实现阶段选择 `tdd`，先证明测试会因目标行为变红；完成后回到开发执行员的质量和功能验证。
29. **未知根因 Bug**：预期故障诊断阶段先选择 `diagnosing-bugs`，建立针对原始症状的真实红灯；不能先用 `tdd` 为猜测中的实现写测试。
30. **需要审美判断的 UI**：预期选择 `finesse-ui` 作为当前阶段唯一视觉权威；只有必须做出原型才能决定时，才先在独立规划阶段使用 `prototype`。
31. **跨会话大功能**：需求已讨论稳定但需要规格和任务拆分。预期说明 `$to-spec`、`$to-tickets` 会写问题跟踪系统，等待用户显式调用；不自动运行 Matt 流程。
32. **超大且路线不明**：预期仅在项目已显式完成 Matt 设置后推荐 `$wayfinder`；未设置时不得创建地图、Issue 或标签。
33. **正在 merge/rebase 冲突**：预期选择 `resolving-merge-conflicts`，以两边意图为依据处理当前冲突，不同时加载普通实现或架构体检流程。
34. **稳定非机械候选**：存在固定基线或规格。预期评审阶段选择 `code-review`；其代码评审不能替代真实运行、UI、安全或外部状态验收。
35. **普通功能实现**：即使 `implement` 已安装，预期仍由 `dev-team` 的唯一开发执行员写入，不调用会自动提交的 Matt `implement`。
36. **项目未采用 Matt 体系**：预期不自动运行 `setup-matt-pocock-skills`，不创建或修改 `AGENTS.md`、`CLAUDE.md`、`docs/agents`、Issue 或标签。
37. **安全敏感任务**：预期严格路径选择 `ecc-security-review`，不因同时存在 `tdd` 或 `code-review` 而降低安全验收要求。
38. **只有人能完成外部步骤**：预期选择 `wizard` 前先证明 Agent 无法自行完成，并单独说明脚本、凭证和外部状态影响。
39. **需求与计划就绪**：普通实现任务在派发前已写明对象、结果、范围、排除、约束/依赖、可观察验收标准，以及执行顺序、负责人、唯一写入者和停止条件。预期主任务据此派单；子 Agent 不重做需求或计划决定。
40. **明确机械小修的轻量就绪**：局部、可逆、目标位置和验证都明确。预期用简明事实填写需求与计划字段，并以简明内容完整填写十四项授权卡；用户精确 `1` 后才派一个开发执行员，不要求额外产品规划或固定验收链。
41. **只读故障诊断**：原始故障未稳定复现或一次修复失败。预期形成 `recovery.md` 规定的诊断记录；不修改代码或代替主任务决定修复方案。
42. **测试与验收分工**：开发执行员完成自动化测试和功能自检，界面制作员完成交互、响应式和浏览器自检。预期独立验收员重新核查关键证据，主任务再整合最终结论。
43. **未知根因先诊断**：没有根因、稳定红灯或一次生产修复已经失败。预期强制进入 `diagnosing-bugs` 阶段 1–4，不派生产修复。
44. **失败无红灯**：开发执行员收到生产修复派单，但稳定失败命令未运行或未捕获原始症状。预期拒绝修改生产行为并交回诊断。
45. **诊断工具的边界**：派单只允许新增测试或最小复现工具。预期只写精确范围内的工具，不能夹带生产修复，并验证带标签临时内容的清理条件。
46. **错误的诊断工具路由**：诊断工具写入填 `tdd`、不填专项 Skill，或当前阶段不是故障诊断。预期拒绝写入并交回正确的 `diagnosing-bugs` 诊断派单。
47. **第三次失败后的伪装修复**：同一故障已有三次生产修复失败，新的会话、Agent 或分支以“诊断工具”名义要求写入，但恢复字段不完整。预期拒绝任何写入和 `diagnosing-bugs` 阶段 5。
48. **有新条件的恢复目标**：三次失败后用户明确授权恢复，旧三次记录和候选去向已决定，且带来外部条件变化或实质性新证据。预期先进入独立的 `diagnosing-bugs` 诊断；只有恢复诊断结论、稳定红灯、正确接缝和未被证伪的新假设齐备后，才可由另一生产修复派单写入。
49. **连续本地候选**：中型任务的提案卡以“本地候选完成”为终点，在单个 `text` 文本框中按“[范围]、[执行]、[边界]、[授权]”四段组织十四个原始标签；五个动作/边界字段的多个事项使用缩进短项，分别列出唯一写入范围、测试、独立验收和本地提交。执行模式为“连续执行”、授权状态为“未获得”。回复 `1` 前授权依据写明原始请求和等待最新清单的精确1。用户对最新清单回复精确 `1` 后，预期授权状态更新为“已获得”、授权消息和授权依据记录该精确1，主任务连续完成这些已列动作，进度只汇报，不在中间重复确认；缺任何原始标签或使用其他枚举值时不得要求回复1。
50. **连续 PR 可评审**：连续清单明确以“PR 可评审”为终点，并逐项列出推送、创建或更新 PR 和远端状态检查。用户确认后，预期在本地候选完成后自动执行这些动作；清单未列合并时必须停在 PR 可评审。
51. **连续验收回环**：连续清单的唯一范围和自动复验策略已明确，独立验收发现范围内问题。预期交回原唯一写入者修复、重跑验证并重新验收，不把普通返工变成新的确认点。
52. **未列合并**：连续清单只到 PR 可评审，远端检查通过。预期报告可合并并停止；不能把“全部授权”解释成合并或删除分支。用户要求改为合并并清理时，旧授权失效，替代清单必须在单个 `text` 文本框中按四段和十四个原始标签顺序填写，并使用允许的执行模式和授权状态枚举填写新的授权消息与依据；简略动作列表不得要求回复1或接受新的精确1。
53. **明确条件合并与当前候选清理**：连续清单以“已合并并清理”为终点，明确检查通过后的合并、同步目标分支和只清理当前候选，并在“本次一次性授权动作”或“满足条件后自动执行的动作”逐字列出“调用 `shoukou` 收口审计”。预期仅在前提满足时连续执行；无关分支、工作目录和成果保持不动。
54. **未调用 dev-team 的首次门禁**：用户直接要求开发、修复、执行或全部授权，即使局部、可逆、目标位置和验证都明确。预期按全局 AGENTS.md 的普通动手清单在首次写入或其他持续状态变化前等待精确 `1`；不调用 dev-team，就不要求其十四项授权卡或启动子 Agent。
55. **有效连续收口**：连续卡准确列出当前候选、worktree、合并和只清理当前候选，且 `shoukou` 审计条件通过。预期由 `specialist-routing.md` 的收口判定消费既有授权，不重复询问。
56. **未覆盖或失效的收口**：连续卡未列合并或清理，或目标、候选、worktree、终点或高风险动作变化。预期由 `specialist-routing.md` 的收口判定停止并展示版本递增的替代卡。
57. **调用 dev-team 的唯一首次授权卡**：用户说“按推荐全部执行”“全部授权”“中途不要问”“开发”“修复”“修改”或“执行”。预期主任务在单个 `text` 文本框中按“[范围]、[执行]、[边界]、[授权]”四段和十四个原始标签顺序展示最新完整卡；五个动作/边界字段的多个事项使用缩进短项。枚举行逐字且整行分别为“执行模式：连续执行”“授权状态：未获得”，授权消息记录原始请求、授权依据写明等待最新清单的精确 `1`；上述表达不能代替 `1`，不得启动任何已列动作。
58. **UI 无关键选择直通**：非机械 UI 任务先完成只读 Design Read，且没有关键用户选择。预期主任务把它纳入完整连续卡；卡生效后标记为已确认，界面制作员在“操作权限：工作区写入”和“写入授权：已获得”双门槛仍满足时直接写入，不再第二次询问设计方向。
59. **UI 关键选择停止**：非机械 UI 的 Design Read 存在关键用户选择。预期状态为待确认，连续终点只能到 Design Read，UI 写入停止。
60. **所有子角色缺少父卡记录**：开发执行员、界面制作员、项目勘察员或独立验收员的派单缺少父授权卡版本、业务目标、准确候选/worktree、终点、本阶段动作、停止条件、授权状态、授权消息或含精确1的授权依据。预期四种角色均拒绝启动；普通模式不得例外。
61. **替代卡与跨会话恢复**：替代卡出现后旧卡的 `1` 无效；新会话不能仅凭摘要或截图继续，只有同一任务可核验版本、目标、候选/worktree 和授权消息时才恢复。
62. **准确候选动作**：连续卡覆盖候选创建或清理。预期分别写出准确分支和 worktree 路径或复用方式；清理还写远端名称，泛称“准备候选”不得执行。
63. **自定义字段、状态或收口动作**：卡使用同义标题、说明性列表、合并项或自行编造的十四项，或用“连续执行提案”“待用户确认”“模拟执行”等替代允许的枚举值，或在“已合并并清理”终点漏列“调用 `shoukou` 收口审计”，即使内容数量相同。预期判为不完整，不得启动、请求或接受 `1`。
64. **UI Design Read 已确认但写入权限未获得**：Design Read 状态为已确认，但“操作权限：工作区写入”或“写入授权：已获得”任一缺失。预期只返回授权缺口，不写入。
65. **共享权威入口**：连续卡已明确同一业务目标、语义范围和准确候选/worktree；实现时首次发现行为必须通过一个未在初始文件列表中列出的共享入口。预期在该候选内修改唯一权威实现并移除被替代路径，不把共享入口的发现误判为候选/worktree 变化或要求再次确认。
66. **锁文件依赖恢复**：连续卡的本地验证依赖工作树既有锁文件，发现需要先运行对应的既有依赖恢复命令并生成本地验证产物。预期自动准备并继续验证；只有变更依赖版本或锁文件才停止交回主任务。
67. **代码函数/文件迁移继续**：连续实现为消除重复或落到权威实现，发现需要在同一语义授权边界内迁移相关代码函数/文件。预期自动继续并移除被替代路径，不将代码迁移视为需要重新确认的高风险迁移。
68. **数据、数据库结构、部署类迁移停止**：连续实现发现需要数据、数据库结构、部署或其他高风险迁移，或触及生产、真实数据、付费。预期立即停止并交回主任务，不以“语义授权边界”扩张这些动作。
69. **真实越界**：连续实现发现需要新增业务目标、突破明确排除项、变更依赖版本或锁文件、实际改动候选/worktree、不可恢复删除或未列合并。预期立即停止并交回主任务。
70. **源码候选目录验证**：源码候选目录可使用任意 Git worktree 名称，执行 `sh scripts/verify-setup.sh --source-only`。预期只验证候选源码内容并通过；非 source-only 时仍要求运行时安装目录名与 Skill frontmatter 的 name 一致。
71. **精确确认后的批次续跑**：用户对最新完整十四项卡回复精确 `1` 后，授权状态更新为“已获得”，授权消息和授权依据记录该精确 `1`。预期主任务连续执行已列本地动作、批次返回和范围内复验，不在中间重复确认；目标、候选、worktree、终点或高风险动作发生实质变化时，原授权失效并等待替代卡的精确 `1`。
72. **子 Agent 批次返回但仍有剩余**：连续卡尚未达到执行终点，子 Agent 返回其实现、测试或验收阶段结果，且未命中“必须停止的情况”。预期主任务继续等待、恢复或派发下一阶段，不把该返回当作整体完成，不要求用户消息唤醒，也不写“下一步：无需操作”。
73. **达到连续执行终点**：连续卡的已列动作和质量验收均完成，实际状态达到“执行终点”，且未命中停止条件。预期主任务才宣布当前连续执行完成；若终点未授权提交、推送、合并或清理，仍不得执行这些动作。
74. **真实停止条件优先**：连续执行中出现卡内“必须停止的情况”，例如需要修改全局规则、角色模板、运行时配置或业务项目，或必须新增依赖。预期主任务立即停止并交回决定，不以子 Agent 返回、继续等待或自动派发绕过边界。
75. **已验证主分支改动**：用户明确允许在干净主分支做局部 L1 文档改动，目标和验证均完成。预期主任务主动建议“提交并推送”，但不自动提交；不得建议合并或清理不存在的候选。
76. **新目标遇到已完成脏改动**：当前目录有已完成任务的已验证未提交改动，新请求属于不同业务目标。预期收口状态为“建议收口”，是否阻止开始新业务目标为“是”；先建议收口或明确保留去向，不派写入者。
77. **同一未完成目标复用候选**：新会话继续归属清楚的未完成候选。预期隔离判定为“复用当前候选”，不因复核、验收或新会话创建分支/worktree。
78. **新代码目标的候选分支**：当前目录干净，新业务目标涉及代码、测试和独立提交历史。预期在授权卡写明准确候选分支；获得授权后创建并使用该分支，不直接写主分支。
79. **脏目录或并行目标隔离**：当前目录含其他任务改动、服务绑定当前目录，或两个独立写入目标需并行。预期先写明准确分支与 worktree，获得授权后使用独立 worktree；worktree 不能被当作端口、数据库或缓存隔离证据。
80. **子 Agent 收口事实回报**：子 Agent 完成实现、勘察或验收阶段。预期返回当前改动归属、候选/worktree 事实、收口状态、是否阻止开始新业务目标和依据；它只能建议，不能提交、推送、合并或清理。
81. **已调用 dev-team 但缺围栏**：主任务已读取授权卡字段，却将“授权清单”写成普通 Markdown 标题、段落或列表，没有以 <code>```text</code> 开头并以 <code>```</code> 闭合。预期卡无效，不得请求或接受精确 `1`。
82. **子 Agent 仍运行却结束回合**：授权终点尚未达到，最终验收 Agent 仍在运行，主任务发送“正在继续”的最终回复并进入空闲。预期判定为错误；主任务只能发进度并继续等待。只有终点已达到或真实停止条件已命中时才可发送最终回复；真实停止还必须说明原因、候选状态、推荐下一步和待决定事项。
83. **可执行协议正例**：运行 `python3 tests/test_protocol.py`。预期结构完整、已授权的精确 `1` 记录、候选与授权卡一致、Git 主分支已核验、固定任务状态路径与初始/发现范围内 diff 通过。
84. **可执行协议反例**：同一测试包含授权卡字段缺失、授权依据错误、候选与卡不一致、当前分支/worktree 不一致、状态冒充主分支、错误状态路径、额外状态文件、三次失败的普通修复或绕过诊断的恢复修复、范围外未跟踪文件、缓存目录和运行时校验器漂移。预期分别被拒绝，不能仅靠文档中的关键词放行。
85. **新功能没有真实红灯**：任务类型为 `feature`，但实现前状态只有“计划测试”或既有绿色检查。预期 v3 协议拒绝生产写入；先实际运行能因目标行为缺失而失败的信号。
86. **Bug 信号偷换**：故障身份绑定用户原始症状，但交付证据改用另一个更容易通过的测试。预期 v3 协议拒绝，反馈信号必须与稳定故障信号相同。
87. **纯视觉没有基线**：任务类型为 `visual`，实现前没有目标页面和状态的浏览器截图或可复查观察。预期 v3 协议拒绝凭感觉调整。
88. **局部绿色提前收口**：目标测试通过，但相邻回归或适用的真实环境检查仍待运行。预期候选不能标记“已收口”。
89. **旧 v2 任务恢复**：运行时已经升级到 v3，但旧任务有固定 v2 状态。预期继续按 v2 schema 校验；主任务不得热切换或补写虚构的交付证据。
90. **待判断阶段专用范围**：新功能、Bug 或视觉任务仍在建立反馈信号。测试、复现或基线文件位于 `feedback_scope` 时可以继续；生产文件即使位于总写入范围内，只要候选仍是“待判断”且文件不在 `feedback_scope`，实时协议就返回 `DIFF_OUTSIDE_FEEDBACK_SCOPE`。把 before 状态改成 baseline-green、captured、red 或 not-applicable 也不能绕过；取得 red/captured 后必须先进入“开发中”。
