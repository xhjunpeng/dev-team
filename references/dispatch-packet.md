# 派单包

派单前必须能写清收益、边界和停止条件。缺少关键字段时不要启动子 Agent。

```text

选择依据：
调用方式：当前阶段自动使用 / 用户显式调用后返回 / 不适用
专项影响：只读 / 项目写入 / 外部状态 / 不适用
专项完成与返回条件：

目标结果：
项目与准确候选路径：

允许读取：

实际生效权限：
唯一写入范围：
质量规范：
目标行为与权威实现：

```

## 需求与计划就绪

主任务在派发实现或验收前填写以下字段；它保留需求与计划决定，子 Agent 只按已确认内容执行。

```text
使用对象或对象群：
目标结果：
范围：
明确排除：
约束/依赖：
可观察的验收标准：
执行顺序：
阶段负责人：
唯一写入者：
交回主任务/停止条件：
```

“需求就绪”指前六项已足以判断做什么和如何验收；“计划就绪”指后四项已足以安排执行和停止。明确、局部、可逆的机械小修可以填写简明事实后直接通过，不要求额外产品规划。字段的具体内容不得复制到角色模板。

写入或验收任务必须填写全部质量字段；不适用时写明原因。找不到权威实现，或干净实现需要扩大唯一写入范围时，任务包保持不完整并退回主任务决定。

## 连续执行授权

连续执行让主任务把一次确认的边界写成一张以结果终点为中心的清单；它不是无限授权。用户明确要求“连续执行”“全部授权”或“中途不要问”时必须使用；中大型任务完成必要只读发现后，主任务应主动给出推荐清单。简单只读、明确机械小修不强制生成清单。

清单在用户确认前必须写清目标、操作对象、范围、影响和明确不会执行的事项，并填写：

```text
执行模式：普通 / 连续执行
执行终点：本地候选完成 / PR 可评审 / 已合并并清理 / 自定义
本次一次性授权动作：
满足条件后自动执行的动作：
自动修复与复验策略：
必须停止的情况：
明确不会执行：
进度汇报方式：只汇报 / 需要确认
授权状态：未获得 / 已获得
授权依据：
```

确认只覆盖最新的连续执行清单。目标、项目、主要方案、执行终点或高风险动作出现实质变化时，原授权失效，主任务重新说明变化并取得授权。主任务收到用户对最新清单的精确 `1` 后，执行到所列终点：已列直接动作无需逐步确认；普通进度只汇报已完成、剩余和下一自动动作。

展示给用户的连续清单必须逐项显式列出上述十个字段，字段不得合并进普通段落。未取得授权时授权依据写明用户当前原始请求和等待的最新清单精确1；取得授权时授权依据记录为最新清单的精确1。缺任一字段不得要求用户回复1或进入执行。

任何终点、项目、主要方案或高风险动作出现实质变化并使旧授权失效时，主任务必须先展示一张完整的替代连续执行清单，逐项显式列出全部十个字段（包括授权状态和授权依据）。不能用简略动作列表、摘要或“新清单”替代。缺任一字段不得请求或接受新的精确1，也不得执行变更后的动作。替代卡确认前的授权依据说明“原授权已失效、用户的新变更请求和等待精确1”；确认后更新为新的精确1。

### 动作边界与终点预设

- **直接动作**是清单已经明确列出的读取、候选操作、派单、写入、测试、验收或 Git 动作；没有列出的提交、推送、PR、合并或删除不能借连续授权执行。
- **条件动作**必须同时写明触发前提和范围。测试失败、独立验收发现的问题、诊断与复验可以在清单已明确的唯一范围内自动循环；同一故障仍以 [recovery.md](recovery.md) 的熔断为准。
- **必须停止**的是未列动作或实质变化：生产、真实数据、密钥、付款、迁移、破坏性回滚或删除，未列的新业务范围、关键未决选择，以及清单未列出的合并。适用的系统、全局和项目规则始终优先。

终点只描述可被清单明确列出的动作边界，不自动扩大 Git 或外部权限：

- **本地候选完成**：可覆盖必要发现、候选准备、唯一写入、测试、独立验收和本地提交。
- **PR 可评审**：在前项基础上，只有清单明确列出时才可包括推送、创建或更新 PR 和远端状态检查。
- **已合并并清理**：在前项基础上，必须明确列出检查通过后的合并、同步目标分支，以及只清理当前候选。
- **自定义**：逐项写出终点和动作，例如“只修复并验收，不提交”。

专项 Skill 字段在每个派单包中都要明确填写。任务清楚时写“不使用”及理由；选择了 Skill 时，先确认它当前可用、调用方式与副作用。仅用户调用的 Skill 未被用户显式调用前，不启动子 Agent、不写项目或外部系统。

## 故障派单字段

仅故障诊断、诊断工具写入、生产修复、故障验收或候选处置任务必须填写：

```text
故障编号：
用户原始症状：
当前生产修复失败次数：
稳定失败命令：
最近一次失败结果：
是否捕获原始症状：
写入类别：只读诊断 / 诊断工具写入 / 生产修复
允许的 diagnosing-bugs 阶段：
本次新证据：
本次可证伪假设：
旧候选和失败改动去向：
恢复目标类型：否 / 诊断 / 生产修复
恢复授权：
旧三次记录与候选去向：
实质性新证据或外部条件：
恢复诊断结论（生产修复才填）：
```

诊断路由和阶段边界见 [specialist-routing.md](specialist-routing.md)；故障身份、计数、诊断工具限制、熔断与恢复资格见 [recovery.md](recovery.md)。角色模板按这些权威规则作出拒绝判断。非故障任务不填写这些字段。

## 角色返回

- **项目勘察员**：事实、证据位置、推测、冲突、未知项和最小下一检查。
- **开发执行员**：改动、文件、权威实现、复用与替换/删除、新增概念或依赖、质量检查、技术债变化、相关自动化测试与功能自检、未运行检查和剩余风险；不倾倒完整日志。
- **界面制作员**：Design Read、页面和状态范围、权威结构与样式、复用与替换/删除、实现文件、质量检查、交互、响应式与浏览器自检、技术债变化和遗留问题。
- **独立验收员**：独立核查的关键证据、功能结果、实现质量、新增技术债、P0-P3、影响、最小修复方向、所需验证、最终结论和未验证边界。

原始日志留在子线程；主任务接收可复查的命令、结果和关键错误。任务协调员等待并整合一次，不重复调查或轮询已知事实。

项目文件写入默认必须派给一个合适的子 Agent。机械小修只派一个开发执行员；不额外派项目勘察员或独立验收员。主任务直接写仅在最新动手清单明确写出“主任务直接写”时允许，并把该授权原文和唯一写入范围写入任务包。

Agent TOML 中的 `sandbox_mode` 是默认配置，不是实际隔离证据。派单前核对父任务当前权限和子线程实际生效权限；只读角色即使运行环境更宽，也必须保持只读并在权限边界不清时停止。
