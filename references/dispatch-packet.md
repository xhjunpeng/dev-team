# 派单包

派单前必须能写清收益、边界和停止条件。缺少关键字段时不要启动子 Agent。

```text
协作模式：已启用
任务包版本：1
任务名称：
使用角色：
当前阶段：需求澄清 / 规划 / 实现 / 故障诊断 / 验收 / 收口
专项 Skill：不使用 / <名称>
选择依据：
调用方式：当前阶段自动使用 / 用户显式调用后返回 / 不适用
专项影响：只读 / 项目写入 / 外部状态 / 不适用
专项完成与返回条件：
派单收益：
目标结果：
项目与准确候选路径：
已知证据：
允许读取：
操作权限：只读 / 工作区写入
实际生效权限：
唯一写入范围：
质量规范：
目标行为与权威实现：
复用项：
替换/删除项：
新增概念、状态、抽象或依赖及理由：
既有债务边界：
质量验收：
明确排除：
用户授权状态：
写入授权：未获得 / 已获得
主任务直接写：不允许 / 最新动手清单已明确授权
已确认 Design Read（UI 任务）：不适用 / 待确认 / 已确认
必须执行的检查：
遇到什么立即停止：
返回格式：
```

## 需求与计划就绪

主任务在派发实现或验收前填写以下字段；它保留需求与计划决定，子 Agent 只按已确认内容执行。

```text
使用对象或对象群：
目标结果：
范围：
明确排除：
约束/依赖：
可观察的验收标准：
执行顺序：
阶段负责人：
唯一写入者：
交回主任务/停止条件：
```

“需求就绪”指前六项已足以判断做什么和如何验收；“计划就绪”指后四项已足以安排执行和停止。明确、局部、可逆的机械小修可以填写简明事实后直接通过，不要求额外产品规划。字段的具体内容不得复制到角色模板。

写入或验收任务必须填写全部质量字段；不适用时写明原因。找不到权威实现，或干净实现需要突破语义授权边界时，任务包保持不完整并退回主任务决定。

## 连续执行授权

连续执行让主任务把一次确认的边界写成一张以结果终点为中心的清单；它不是无限授权。用户明确要求“连续执行”“全部授权”或“中途不要问”时必须使用；中大型任务完成必要只读发现后，主任务应主动给出推荐清单。简单只读、明确机械小修不强制生成清单。

清单在启动前必须写清目标、操作对象、范围、影响和明确不会执行的事项，并填写：

```text
执行模式：普通 / 连续执行
连续清单版本：
业务目标：
准确候选与 worktree：
执行终点：本地候选完成 / PR 可评审 / 已合并并清理 / 自定义
本次一次性授权动作：
满足条件后自动执行的动作：
自动修复与复验策略：
必须停止的情况：
明确不会执行：
进度汇报方式：只汇报 / 需要确认
授权状态：未获得 / 已获得
授权消息：
授权依据：
```

连续清单有且只有以下三种启动路径；其中本地实施授权的边界以全局 AGENTS.md 的“执行与确认”“回复方式”为准，本节只记录并传递该授权：

- **明确连续授权**：用户已对当前明确目标说“按推荐全部执行”“全部授权”或“中途不要问”。主任务仍先展示十四个原始字段；执行模式填“连续执行”，授权状态填“已获得”，授权消息记录原话，授权依据记录可直接开始。不得以“授权类型”替代任何字段。
- **已有实施授权**：用户明确要求开发、修复、修改或执行，且全局规则已授予当前明确范围内的本地实施授权。主任务仍先展示十四个原始字段；执行模式填“连续执行”，授权状态填“已获得”，授权消息记录该明确请求，授权依据记录全局规则已授予本地实施授权；不等待精确 `1`，直接开始已列动作。
- **提案确认**：用户只要求方案或清单。完整清单的执行模式填“连续执行”、授权状态填“未获得”，主任务必须等待用户对最新清单的精确 `1` 后才将授权状态更新为“已获得”并开始。

枚举行硬门槛：执行模式行必须逐字且整行仅为“执行模式：普通”或“执行模式：连续执行”；授权状态行必须逐字且整行仅为“授权状态：未获得”或“授权状态：已获得”。解释另起字段内容行，不得追加在枚举行；不得使用“连续执行提案”“待用户确认”“模拟执行”等同义状态。

授权只覆盖当前版本的连续执行清单。目标、项目、主要方案、执行终点、高风险动作、准确候选或 worktree 出现实质变化时，原授权失效，主任务重新说明变化并取得授权。首次发现同一候选/worktree 内的权威实现、共享入口或相邻测试接缝，不是候选/worktree 的实质变化。已启动的卡执行到所列终点：已列直接动作无需逐步确认；普通进度只汇报已完成、剩余和下一自动动作。

### 主任务终点门禁

子 Agent 返回只表示本派单阶段结束，不表示主任务或业务目标完成。主任务在每次子 Agent 返回后，必须以当前连续卡逐项核对：

- 已达到执行终点时，才可宣布当前连续执行完成；
- 命中“必须停止的情况”时，立即停止并按卡和适用规则交回用户或主任务决定；
- 未达到执行终点且未命中停止条件时，主任务必须继续等待、恢复或派发下一阶段，不得把批次完成当作整体完成、要求用户消息唤醒，或把普通进度写成“下一步：无需操作”。

这一门禁不扩大卡内动作、Git 或外部系统权限；下一阶段仍须在连续授权传递字段和本阶段允许动作内执行。

渲染硬门槛：展示给用户的初始卡和替代卡必须按上述十四个原始字段标签、原始顺序逐行呈现；不得用同义标题、说明性列表、合并项或另起十四项替代。字段值未知时明确写“待只读核对”，但标签不得省略。授权消息记录触发授权的原始消息或精确1；提案确认的未授权卡在授权依据中写明用户当前原始请求和等待的最新清单精确1；已授权卡记录明确连续授权的原始消息或最新清单的精确1。缺少任何原始标签或使用未允许的枚举值的卡不是完整卡，不得启动、请求或接受精确1。

任何使旧授权失效的实质变化，主任务必须先展示一张版本递增的完整替代连续执行清单，逐项显式列出全部十四个字段（包括授权状态、授权消息和授权依据）。不能用简略动作列表、摘要或“新清单”替代。替代卡按上述三种启动路径取得授权；缺任一字段不得请求或接受新的精确1，也不得执行变更后的动作。

新会话或新线程不得仅凭摘要、截图或旧卡继承授权。只有同一任务恢复时能核验连续清单版本、业务目标、准确候选与 worktree、以及授权消息，才可继续执行。

### 动作边界与终点预设

- **直接动作**是清单已经明确列出的读取、候选操作、派单、写入、测试、验收或 Git 动作；没有列出的提交、推送、PR、合并或删除不能借连续授权执行。
- **语义授权边界**以同一业务目标、目标行为、明确排除和质量验收定义；派单中的唯一写入范围用于约束并发所有权，不是冻结的文件白名单。为完成已授权行为，首次定位权威实现或共享入口、补充相邻测试、迁移相关代码函数/文件、按既有锁文件恢复本地依赖、生成本地验证产物，以及验收发现的范围内返工，都属于普通范围内推进。
- **条件动作**必须同时写明触发前提和语义授权边界。测试失败、独立验收发现的问题、诊断与复验可以在清单已明确的语义授权边界内自动循环；同一故障仍以 [recovery.md](recovery.md) 的熔断为准。
- **必须停止**的是未列动作或真实边界变化：新增业务目标、突破明确排除项、依赖版本或锁文件变更、生产、真实数据、密钥、付款、数据、数据库结构、部署或其他高风险迁移、破坏性回滚或删除、准确候选/worktree 的实际变更、关键未决选择，以及清单未列出的合并。适用的系统、全局和项目规则始终优先。

终点只描述可被清单明确列出的动作边界，不自动扩大 Git 或外部权限：

- **本地候选完成**：可覆盖必要发现、候选准备、唯一写入、测试、独立验收和本地提交。
- **PR 可评审**：在前项基础上，只有清单明确列出时才可包括推送、创建或更新 PR 和远端状态检查。
- **已合并并清理**：在前项基础上，必须明确列出检查通过后的合并、同步目标分支，以及只清理当前候选；“本次一次性授权动作”或“满足条件后自动执行的动作”必须逐字包含“调用 `shoukou` 收口审计”，缺失则卡不完整，不得启动。收口授权判定见 [specialist-routing.md](specialist-routing.md)。
- **自定义**：逐项写出终点和动作，例如“只修复并验收，不提交”。

专项 Skill 字段在每个派单包中都要明确填写。任务清楚时写“不使用”及理由；选择了 Skill 时，先确认它当前可用、调用方式与副作用。仅用户调用的 Skill 未被用户显式调用前，不启动子 Agent、不写项目或外部系统。

## 连续授权传递

连续模式的每个子任务都必须附带以下字段；普通模式不填写。子任务只校验和执行这些字段，不重新解释用户授权：

```text
父连续清单版本：
父业务目标：
父准确候选与 worktree：
连续执行终点：
本阶段允许动作：
必须停止的情况：
授权依据：
```

连续模式缺任一字段、字段与父卡不匹配，或要求超出本阶段允许动作和停止条件时，子任务不得启动或继续，交回主任务。子任务返回后，主任务仍按“主任务终点门禁”决定继续、停止或完成；子任务不得自行宣布连续执行完成。

## 故障派单字段

仅故障诊断、诊断工具写入、生产修复、故障验收或候选处置任务必须填写：

```text
故障编号：
用户原始症状：
当前生产修复失败次数：
稳定失败命令：
最近一次失败结果：
是否捕获原始症状：
写入类别：只读诊断 / 诊断工具写入 / 生产修复
允许的 diagnosing-bugs 阶段：
本次新证据：
本次可证伪假设：
旧候选和失败改动去向：
恢复目标类型：否 / 诊断 / 生产修复
恢复授权：
旧三次记录与候选去向：
实质性新证据或外部条件：
恢复诊断结论（生产修复才填）：
```

诊断路由和阶段边界见 [specialist-routing.md](specialist-routing.md)；故障身份、计数、诊断工具限制、熔断与恢复资格见 [recovery.md](recovery.md)。角色模板按这些权威规则作出拒绝判断。非故障任务不填写这些字段。

## 角色返回

- **项目勘察员**：事实、证据位置、推测、冲突、未知项和最小下一检查。
- **开发执行员**：改动、文件、权威实现、复用与替换/删除、新增概念或依赖、质量检查、技术债变化、相关自动化测试与功能自检、未运行检查和剩余风险；不倾倒完整日志。
- **界面制作员**：Design Read、页面和状态范围、权威结构与样式、复用与替换/删除、实现文件、质量检查、交互、响应式与浏览器自检、技术债变化和遗留问题。
- **独立验收员**：独立核查的关键证据、功能结果、实现质量、新增技术债、P0-P3、影响、最小修复方向、所需验证、最终结论和未验证边界。

原始日志留在子线程；主任务接收可复查的命令、结果和关键错误。任务协调员等待并整合一次，不重复调查或轮询已知事实。

项目文件写入默认必须派给一个合适的子 Agent。机械小修只派一个开发执行员；不额外派项目勘察员或独立验收员。主任务直接写仅在最新动手清单明确写出“主任务直接写”时允许，并把该授权原文和唯一写入范围写入任务包。

Agent TOML 中的 `sandbox_mode` 是默认配置，不是实际隔离证据。派单前核对父任务当前权限和子线程实际生效权限；只读角色即使运行环境更宽，也必须保持只读并在权限边界不清时停止。
