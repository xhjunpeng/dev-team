# UI 路由

本文件的 UI 专项规则优先于通用快速路径。涉及视觉层级、布局、交互方式、响应式、动效或组件状态，且需要审美判断时，派界面制作员；已有精确答案的机械 UI 修改派开发执行员。所有 UI 写入同时执行 [engineering-quality.md](engineering-quality.md)，结构、状态和样式各自只保留一个权威实现。主任务不写 UI，除非用户在最新动手清单中明确授权“主任务直接写”。纯接口接线、数据修复、明确条件显示和无设计判断的机械修复留给开发执行员。

## 单一设计权威

默认使用 `finesse-ui`，一次任务只能有一个决定视觉方向的 Skill：

- 新页面或完整 UI：`craft`。
- 已有页面升级：`redesign`。
- 只读评价：独立验收员使用 `audit`。
- 单一按钮、输入、卡片或弹窗仍需布局、视觉层级、状态或审美判断：界面制作员走 `finesse-ui component-scope`。已有精确答案的机械 UI 修改不加载此流程，交给开发执行员直接执行相称检查。
- “太乱、太空、太普通、动效不对”：使用对应定向命令，不整页重建。

精确照图时可以用 `product-design:image-to-code` 替代本次 `finesse-ui`；`shadcn` 只协助组件实现；图片生成必须在 `finesse-ui` 先提出具体图片位置和来源、用户另行确认后才进行。

## 设计门禁

界面制作员先输出 Design Read：可见方向、保留内容、修改范围、状态、权威结构与样式位置、复用项、替换/删除项、图片计划、验证方式和最可能的反对点。主任务把它与最新执行卡合并；未取得相应写入授权前只读停止。

已有产品默认保留真实 AppShell、导航、组件、token、业务规则和页面所有权；先确认浏览器实际服务的候选、进程和路由，再评价视觉结果。

## 验收分离

界面制作员负责设计、实现和自检，不能独立验收自己。需要独立 UI 验收时，新建只读独立验收员检查准确候选、真实浏览器流程、响应式、可访问性、控制台、网络，以及重复选择器、后置覆盖、平行组件或状态和未验证外部状态。功能与视觉正确但实现质量不通过时仍不验收。
