# 失败恢复与三次熔断

同一故障没有可靠反馈循环时，不允许开始猜测式修复。需要难问题诊断时使用 `diagnosing-bugs`：先建立能针对用户原始症状变红、修复后变绿的测试、命令、请求或浏览器步骤。

## 项目勘察员的故障诊断模式

故障诊断阶段由项目勘察员只读执行：收集事实，不修改代码，也不做产品、架构、授权或修复决定。返回记录必须包含：

```text
原始症状：
可靠复现信号：
可证伪假设及预测：
证据位置：
已排除项：
未知项：
交回主任务的条件：
```

可靠复现信号优先使用能对原始症状变红的测试、命令、请求或浏览器步骤。没有可靠信号时，交回条件应写明还缺少的环境、权限或观察；不得用猜测性改动补足。主任务据此决定是否派发下一次有边界的修复。

## 计数

一次修复尝试等于：一个可证伪假设、一次有边界的代码改动、一次针对原始故障信号的验证。只读调查不计数；不同故障分别编号。

每次记录：

```text
故障编号：
原始现象：
复现命令或步骤：
期望 / 实际：
本次假设与可验证预测：
修改文件：
验证结果：
假设为何成立或被证伪：
当前 diff 是否可保留：
下一次必须获得的新证据：
失败次数：
```

## 熔断

- **第一次失败**：立即停止继续打补丁，记录被证伪的假设；项目勘察员可按故障诊断模式只读补证。
- **第二次失败**：原执行员退出该故障，冻结写入；由全新上下文的项目勘察员按故障诊断模式核验故障信号和候选状态。
- **第三次尝试前**：必须有不同的新假设和新证据，说明前两次 diff 的去向，并展示新的执行卡；不能自动升级模型后继续。
- **第三次仍失败**：硬停止并标记阻塞。任何 Agent 都不得以换模型、换 Agent、新分支或新 worktree 的方式进行第四次。

每次失败后先检查共享文件和已有成果。不要自动 reset、restore、删除或覆盖失败改动；由任务协调员确认哪些属于本次尝试、哪些可保留，以及撤销是否在授权范围内。

## 阻塞报告

报告已验证事实、三次假设与证据、当前候选和 diff、可保留与未确认内容、缺失环境或权限、恢复工作需要的新条件。测试未再报错不等于根因已解决。
