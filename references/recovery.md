# 原始故障、尝试与恢复

同一故障绑定用户原始症状与原始检查/观察入口。新会话、Agent、模型、分支或工作目录保持同一身份和失败历史。机器只校验记录一致性，主任务核对证据是否真的经过原始故障路径。

## 证据与尝试

可复现 Bug 使用稳定原始信号：已实际执行、捕获原始症状并有根因证据后，才修改生产行为；修复后检查同一信号。偶发故障先保存日志、追踪、发生条件和样本，允许在精确反馈范围增加诊断能力。v5 的 `bug-diagnosis` 只交付可诊断性，持续限制为 `feedback_scope`，必须写明未验证边界，不能声称修复。获得可复现原始信号后，由主任务记录证据并进入 `bug-repro` 修复阶段。

一次计入的失败是：针对同一原始故障提出一个可证伪假设、改变生产行为、实际检查原始信号后证伪该假设。一次命令拼写、测试语法、工具调用或环境启动错误不自动算修复失败，分别记入 `diagnostic_events` 并保存证据。原始故障仍失败不能为了少计数改称环境问题；真正证伪同一假设的记录写入 `failure_records`，`production_failure_count` 等于这些记录数。

诊断工具写入有精确范围、行为权限和临时清理条件；它只帮助观察，不夹带生产修复。采用诊断方法和阶段边界见 [specialist-routing.md](specialist-routing.md)。非故障任务不伪造故障身份；普通开发检查失败也不能自动套用原始 Bug 计数。

## 三次停止

第一次假设被证伪后停止打补丁，记录新证据再诊断；第二次后冻结原执行员写入，用全新只读上下文核对信号与候选。第三次前必须有新假设、新证据、旧 diff 去向和明确执行授权。

第三次仍失败，当前候选阻塞，禁止第四次普通修复及借诊断工具写入绕行。保留三条失败记录，只做只读诊断、证据整理与已授权候选处置。任何 Agent 不能通过换身份、模型或目录清零。撤销失败改动前核对归属与授权，保留其他人的成果。

## 明确恢复

三次后只有用户明确授权且存在实质性新证据或外部条件变化时，建立同一故障的恢复阶段。先 `recovery-diagnosis`，保留全部失败 ID、旧授权、独立诊断授权和证据；诊断仅阶段 1–4。随后另一个有明确授权的 `recovery-repair` 阶段才可改生产行为，要求完成的诊断结论、同一原始信号、未被证伪的新假设和准确故障对象。恢复授权版本必须晚于诊断，不能用一次授权跳过两阶段。

v5 恢复可使用明确自然语言同意，授权快照保留非空消息/依据，当前动作需显式包含 `recovery-repair`、故障 ID、影响和回滚；v2–v4 继续要求旧精确 `1` 快照。`failure_records` 永远保留，恢复失败追加记录，不能重用已被证伪假设。

返回原始症状、命令/观察、期望与实际、假设、证据位置、当前 diff 去向、计数、未知项和下一步所需的新条件。测试暂时不报错不等于根因解决。
