# 失败恢复与三次熔断

同一故障没有可靠反馈循环时，不允许开始猜测式修复。路由条件和 `diagnosing-bugs` 阶段边界见 [specialist-routing.md](specialist-routing.md)；本文件只定义故障身份、信号、尝试、熔断与恢复。

## 故障身份与稳定红色失败信号

同一故障绑定“用户原始症状 + 稳定失败命令”。新会话、模型、Agent、分支或工作目录不改变这个身份，也不清零失败次数。稳定红色失败信号是已经运行过的命令、测试、请求或浏览器步骤：它实际经过故障路径、捕获用户的原始症状、结果可重复，并能在修复后转绿。没有这种信号，不能修改生产行为。

## 诊断工具写入与生产修复尝试

“诊断工具写入”只包括测试、最小复现脚本，或带唯一标签和清理条件的临时诊断代码。它需要单独写入授权、精确文件范围和清理条件，不能与生产修复同一派单，不能改变生产行为，也不计生产修复尝试。它始终属于故障诊断阶段，并遵循 [specialist-routing.md](specialist-routing.md) 的专项和阶段边界。

一次“生产修复尝试”必须同时是：一个可证伪假设、一次改变生产行为的改动、一次对同一稳定红色失败信号的验证。只读诊断不计数。每个假设最多一次生产改动；已被证伪的假设不得在恢复任务中重试。

## 诊断记录

故障诊断必须形成以下记录：

```text
原始症状：
可靠复现信号：
可证伪假设及预测：
证据位置：
已排除项：
未知项：
交回主任务的条件：
```

可靠复现信号优先使用能对原始症状变红的测试、命令、请求或浏览器步骤。没有可靠信号时，记录缺少的环境、权限或观察；不得用猜测性改动补足。

## 计数

每次记录：

```text
故障编号：
原始现象：
复现命令或步骤：
期望 / 实际：
本次假设与可验证预测：
修改文件：
验证结果：
假设为何成立或被证伪：
当前 diff 是否可保留：
下一次必须获得的新证据：
失败次数：
```

## 熔断

- **第一次失败**：立即停止继续打补丁，记录被证伪的假设；后续阶段由专项路由决定。
- **第二次失败**：冻结原执行员的写入，要求全新只读上下文核验故障信号和候选状态。
- **第三次尝试前**：必须有不同的新假设和新证据，说明前两次 diff 的去向，并展示新的执行卡；不能自动升级模型后继续。
- **第三次仍失败**：当前目标和候选硬停止并标记阻塞。只允许只读诊断、证据整理与候选处置；禁止 `diagnosing-bugs` 阶段 5、生产修复和诊断工具写入。任何 Agent 都不得以换会话、换模型、换 Agent、新分支或新 worktree 的方式进行第四次。

每次失败后先检查共享文件和已有成果。不要自动 reset、restore、删除或覆盖失败改动；由任务协调员确认哪些属于本次尝试、哪些可保留，以及撤销是否在授权范围内。

## 恢复目标

三次失败后的新“恢复目标”不是重试入口，也不解除原目标和候选的硬停止。只有派单中的恢复字段完整、用户明确授权、旧三次记录和候选去向已携带，且存在实质性新证据或外部条件变化时，才是可以启动的新目标。恢复目标沿用故障身份和失败历史，不得复用已被证伪的假设。

合格恢复目标先进入诊断；诊断只按专项路由的故障诊断边界进行。只有恢复诊断结论已经明确，且后续独立生产修复派单另有稳定红色失败信号、根因证据、正确回归接缝和新的可证伪假设时，才可进行该新目标的生产修复。具体恢复字段定义以 [dispatch-packet.md](dispatch-packet.md) 为准。

## 阻塞报告

报告已验证事实、三次假设与证据、当前候选和 diff、可保留与未确认内容、缺失环境或权限、恢复工作需要的新条件。测试未再报错不等于根因已解决。
