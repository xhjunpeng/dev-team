# Git 候选生命周期

适用的全局和项目 Git 规则是权威来源。这里提供统一判断过程，不授权创建、切换、提交、合并或删除。

## 写入前门禁

先核对项目根、主分支、当前分支、状态、worktree、已有候选、任务归属和合并状态，并填写候选台账。

```text
只读任务
→ 不创建候选

同一业务目标已有候选
→ 必须复用；新会话、修复、复核和验收不另建候选

新业务目标，当前只有一个任务，当前目录干净且没有运行态绑定
→ 获得明确授权后可创建候选分支并继续使用当前目录

并行任务、主目录含其他改动、服务绑定当前目录、高风险或长任务
→ 获得明确授权后使用独立分支和 worktree

归属不清或存在多个疑似候选
→ 停止写入，先输出候选台账
```

worktree 只隔离文件目录，不自动隔离端口、数据库、缓存、依赖或外部服务；运行态必须另行核对。

连续清单覆盖创建候选时，必须明确写出准确分支名以及 worktree 路径或复用方式；泛称“准备候选”不是授权。连续清理同样必须明确写出当前候选的分支、worktree 和远端名称，并同时满足下方审计条件。其他情形仍按适用规则取得授权。

## 并行边界

- 每个项目默认一个活跃可写候选；并行目标必须经过明确批准。
- 两个写入者只有在接口已经固定、文件所有权完全分离时才能并行。
- 共享类型、状态模型、迁移、组件或页面存在重叠时改为串行。
- 子 Agent 不得自行创建新候选来绕过冲突、失败或复核。

## 何时提醒收口

- 当前业务目标已完成所需验收。
- 对应 PR 已合并。
- 用户暂停或放弃任务。
- 准备开始同项目的新业务目标。
- 同项目出现第二个活跃候选。

## 何时允许申请清理

必须同时证明：

- 候选已合并，或有可靠 PR / Git 祖先关系证据。
- worktree 干净，未跟踪和未提交内容已确认归属。
- 独有提交全部有去向。
- 没有运行服务、任务、终端或其他引用继续使用目录。
- 清理目标与授权准确对应。

不满足时标记为“继续开发”“阻塞”或“恢复候选”，并保留。真正的审计、合并和清理使用 `shoukou`；不要在本流程中复制其详细规则。
