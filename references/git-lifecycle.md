# Git 候选生命周期

适用的全局和项目 Git 规则是权威来源。这里提供统一判断过程，不授权创建、切换、提交、合并或删除。

## 任务隔离前置判断

每个新业务目标、恢复候选或写入前，先核对项目根、主分支、当前分支、状态、worktree、已有候选、任务归属和合并状态，并填写候选台账。子 Agent 只返回事实和建议；主任务负责隔离、收口和 Git 决定。

```text
只读任务
→ 不创建候选

同一未完成业务目标已有归属清楚的候选
→ 必须复用；新会话、修复、复核和验收不另建候选

新业务目标，当前目录干净、没有运行态绑定，且用户明确允许直接在由 Git 元数据核验的主分支做局部 L1 文档改动
→ 获得明确授权后可直接写入主分支；完成后建议提交并推送，不建议合并

新业务目标，涉及代码、配置、测试、脚本、跨会话交付、PR 或需要独立提交历史
→ 获得明确授权后创建候选分支；当前目录干净且没有运行态绑定时可在当前目录使用该分支

并行任务、当前目录含其他任务改动、服务绑定当前目录、高风险或长任务
→ 获得明确授权后使用独立分支和 worktree

当前目录有已完成任务的未收口改动、归属不清改动或多个疑似候选
→ 不开始新业务目标；先输出候选台账并建议收口或要求明确保留去向
```

worktree 只隔离文件目录，不自动隔离端口、数据库、缓存、依赖或外部服务；运行态必须另行核对。

主分支直接写的本地可执行门槛以 [executable-protocol.md](executable-protocol.md) 的默认实时检查为唯一机器规则：它先确定当前分支；若该分支等于优先解析的 `refs/remotes/origin/HEAD`（或该引用缺失时的仓库配置 `dev-team.primaryBranch`），隔离只能为“主分支直接写”，状态 `primary_branch` 和候选分支都必须匹配。不得把实际主分支自报为“当前目录候选分支”，也不得由状态把当前候选自报为主分支。普通非主分支候选不需要成功解析主分支。其余隔离决策仍由本文件和实际 Git 事实决定。

连续清单覆盖创建候选时，必须明确写出准确分支名以及 worktree 路径或复用方式；泛称“准备候选”不是授权。连续清理同样必须明确写出当前候选的分支、worktree 和远端名称，并同时满足下方审计条件。其他情形仍按适用规则取得授权。

## 并行边界

- 每个项目默认一个活跃可写候选；并行目标必须经过明确批准。
- 两个写入者只有在接口已经固定、文件所有权完全分离时才能并行。
- 共享类型、状态模型、迁移、组件或页面存在重叠时改为串行。
- 子 Agent 不得自行创建新候选来绕过冲突、失败或复核。

## 收口判断与新任务门禁

子 Agent 完成阶段时必须返回：当前改动归属、候选与 worktree 事实、收口状态、是否阻止开始新业务目标和依据。允许的收口状态只有“继续开发 / 建议收口 / 阻塞”。它不能提交、推送、合并、清理或代替主任务决定。

主任务在以下任一情况主动给出收口建议，而不是把“未获执行授权”写成“不建议收口”：

- 当前业务目标已完成所需验收，改动归属清楚且存在未提交改动、未推送提交或待合并 PR。
- 对应 PR 已合并，且存在当前候选分支或专用 worktree。
- 用户暂停、放弃或准备开始同项目的新业务目标。
- 同项目出现第二个活跃候选，或当前目录出现不属于同一未完成目标的脏改动。

建议动作按事实区分：主分支上的已验证改动建议“提交并推送”；候选分支建议“提交、推送和 PR”；已合并且满足清理条件的候选建议“同步目标分支并清理当前候选”。建议不授予任何 Git 动作；只有最新授权卡明确列出时才执行。

除同一未完成业务目标的明确复用外，只要当前目录不干净，就阻止开始新业务目标。主任务先给出“收口 / 明确保留 / 建立独立 worktree”三种可选去向；未决定前不得派写入者。

## 何时允许申请清理

必须同时证明：

- 候选已合并，或有可靠 PR / Git 祖先关系证据。
- worktree 干净，未跟踪和未提交内容已确认归属。
- 独有提交全部有去向。
- 没有运行服务、任务、终端或其他引用继续使用目录。
- 清理目标与授权准确对应。

不满足时标记为“继续开发”“阻塞”或“恢复候选”，并保留。真正的审计、合并和清理使用 `shoukou`；不要在本流程中复制其详细规则。
