# 工程质量门禁

目标是**最小可维护实现**：用完成当前需求所需的最少概念、状态、分支、依赖和权威实现，清楚表达行为。简洁不等于行数最少；必要的业务复杂度应当显式、可测试，额外复杂度应当移除。

本门禁适用于代码、UI、测试、配置、脚本和迁移写入。项目已有检查命令可作为验证信号，但不改变本门禁的判定。

## 动手前：确定改动形状

写入任务先写清：

```text
目标行为：
权威实现：当前负责该行为的唯一源码、样式、配置或数据模型
复用项：已有组件、函数、类型、token、接口或测试工具
替换/删除项：本次完成后不再需要的旧路径、旧规则或重复实现
新增概念、状态、抽象或依赖及理由：为什么当前就需要
既有债务边界：触及范围内已存在但本次不处理的内容
质量验证：如何证明没有新增重复、覆盖层、死路径或未批准债务
```

找不到权威实现，或干净实现必须修改当前授权范围以外的内容时，在写入前停止并交回任务协调员决定范围。不能用后置覆盖、复制一套逻辑或保留新旧并行路径来绕过这个决定。

## 实现必须保持的事实

- **一个行为只有一个权威实现。** 修改行为来源并移除已被替代的路径；兼容路径只有在任务明确要求且有退出条件时保留。
- **先复用，再新增。** 已有组件、类型、token、接口或工具足够时直接复用。新抽象应当立即减少当前重复或隔离真实边界；单一调用者的抽象需要具体边界理由，不为假设中的未来需求搭框架。
- **代码为阅读服务。** 选择职责集中、控制流清楚、命名直接的实现；不以压缩行数换取隐藏状态、晦涩技巧或额外耦合。
- **改动围绕当前目标闭合。** 一并完成实现所需的局部整理和旧路径删除，不夹带无关重构，也不把必要整理推成以后再做。v4 协议中的 `deferred` 是可追踪的既有债务，不是继续扩大当前候选的理由；`scope-change` 必须停止并由主任务决定。
- **测试验证行为。** 测试覆盖目标结果和相关失败信号；跳过测试、注释掉旧代码或留下待办不能作为完成状态。
- **新增已知技术债为零。** 触及范围外的既有债务不要求顺手清理；如果它阻止干净实现，停止并说明，不在其上继续叠加。

## 需要整理后才能完成的信号

出现以下任一信号时，先回到权威实现整理；确有必要保留时，任务包必须记录原因、边界、退出条件和独立验收：

- 在文件尾部或更高优先级位置追加规则，只为覆盖前面的规则。
- 同一选择器、业务判断、校验、查询、状态模型或组件出现第二套定义。
- 复制现有代码后只改少量名称、条件或样式，形成平行实现。
- 新旧路径同时存活，但没有明确兼容期限和删除条件。
- 新增包装层、通用工具、依赖或状态，却没有减少当前整体复杂度。
- 替换既有行为时只增加代码，没有处理已失效的旧实现。
- 通过 `!important`、选择器权重或加载顺序争夺控制权，而不是确定样式归属。

这些是结构信号，不使用统一文件行数、函数行数或净增行数作为机械结论。项目已有复杂度、重复率或体积检查时运行并报告结果；质量判断仍依据权威实现、重复、耦合和债务变化。

## 写入者自检

完成前必须：

1. 检查实际 diff 和被修改行为的完整权威实现，不只看自己新增的行。
2. 搜索触及范围内的重复定义、后置覆盖、新旧并行路径、死代码、跳过测试和待办。
3. 运行项目已有的格式、静态检查、测试和目标行为验证；Git 项目同时运行 `git diff --check`。
4. 报告权威实现、复用项、替换/删除项、新增概念或依赖及理由、质量检查结果和技术债变化。

如果无法证明新增已知技术债为零，结果保持未完成。

## 验收结论

验收分开报告：

```text
功能结果：通过 / 不通过 / 未验证
实现质量：通过 / 不通过 / 未验证
新增技术债：零 / 已批准例外 / 未批准
最终结论：仅当前两项通过，且没有未批准的新技术债时通过
```

主任务对每个写入 diff 做质量复核。触及已有热点、重复或覆盖区，共享接口、状态或数据模型，结构性重构，失败修复记录，或需要明显架构判断时，使用全新只读独立验收员。功能测试通过不能替代实现质量通过。
