# 工程质量与固定验收

目标是最小可维护实现：每个行为有一个权威来源，复用已有能力，处理被替代路径，以清楚的接口和控制流表达必要复杂度。开始时记下目标行为、权威实现、复用项、替换/删除项、必要新增概念或依赖、既有债务边界，以及固定验收；不按文件行数或净增行数裁定质量。

完成前看实际 diff 和完整权威实现，检查重复定义、后置覆盖、平行状态、死路径、跳过测试及不必要依赖。运行与影响相称的既有检查；功能正确不能掩盖无法维护的实现。测试验证可观察行为，不为可逆小改动编写镜像测试或用文案关键词证明流程正确。

## 质量例外

v5 允许有明确理由的局部质量取舍，记录 `quality_exceptions`：原因、边界、退出条件、当前授权版本和明确同意的证据。待决定例外不允许完成；已批准例外必须在最终报告和独立验收中可见。例外只适用于实现取舍，不能豁免安全、权限、固定目标检查、当前阻塞或独立验收。不能声称机器证明了“绝对零债务”。旧 v2–v4 任务继续按原零新增已知债务要求处理，未批准时保持未完成。

## 发现分流

v4/v5 共同使用冻结的 `scope_control` 和三类 `finding_records`：

- `current-blocker`：由当前改动引入/加重，或完成固定目标必需，有因果证据；范围内修复和复验。
- `deferred`：无关旧问题、建议或不影响固定验收的发现，只记录，不阻塞完成。
- `scope-change`：新增业务目标或改变冻结边界，停止并交回主任务；用户未决定前不写入、不自动创建任务。

实现者与验收者只建议分类，主任务负责固定范围与标准。通过后不因新建议反复提高标准。

## 验证类型

Bug 先捕获用户原始症状与根因证据。可复现故障验证原始信号红转绿；偶发故障可以先以日志/追踪实现可诊断性，保留未复现、未证实修复的边界，不把未再出现写成已修复。新功能选择相称的目标检查，不强制先造红灯；用户要求 TDD 时按 TDD 执行。已有 UI 保留准确页面/状态基线，全新 UI 明确旧基线不适用并验证新页面实际流程。详见 [executable-protocol.md](executable-protocol.md) 与 [ui-routing.md](ui-routing.md)。

最终分别报告功能结果、实现质量、已批准/未批准例外和未验证边界。固定检查完成、无当前阻塞、无未决范围变化或未批准例外后，候选才可完成。高风险必须独立验收；其他独立验收按路由决定。
