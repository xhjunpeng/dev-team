# 项目发现

只收集当前任务需要的事实。环境和项目文件是事实来源，不在 Skill 中维护项目副本。

## 最小发现

1. 确认当前目录、项目根目录和任务目标。
2. 读取当前范围适用的规则和它们直接指向的资料。
3. 识别技术栈、现有脚本、测试入口和真实源文件。
4. 区分已验证事实、合理推测和待验证事项。

只读问题到此即可。不要因为调用了协作 Skill 就启动服务、创建候选或扫描全部仓库。

## 写入前补充

写入任务还要确认：

- Git 主分支、当前分支、未提交和未跟踪内容。
- 已有候选、worktree、任务归属和合并状态。
- 当前请求与已有候选的关系：同一未完成业务目标、新业务目标或归属不明；按 [git-lifecycle.md](git-lifecycle.md) 判断复用、分支、worktree 或先收口。
- 若当前目录不干净，逐项确认改动是否属于同一未完成目标；已完成、无关或归属不明的改动阻止新业务目标写入，直到收口或明确保留去向。
- 本轮唯一写入范围，以及是否与用户或其他 Agent 重叠。
- 项目规定的构建、测试、格式和验收命令。
- 当前行为的权威实现、可复用项、需要替换或删除的旧路径，以及触及范围内已有的重复、覆盖区或复杂度热点。
- 项目已有的代码质量、重复率、复杂度或体积检查；没有时不发明机械行数阈值。
- 需要的凭证、外部系统、费用和数据边界；不要读取或展示秘密。

运行态只有在任务依赖真实页面、服务、端口、数据库或进程时才检查。此时核对监听进程、PID、命令、cwd、路由和依赖，不把“端口可用”或“启动日志”当作目标服务证据。

## 连续任务前置准备

在展示或启动首次连续执行清单前，除上述写入前补充外，还要确认同一业务目标的落地入口：

- 找到目标行为的权威实现，以及它必须经过的共享入口、相邻测试接缝或需要迁移的函数/文件；把这些作为语义范围的事实，不把首次发现它们误判为新业务范围。
- 若本地验证依赖工作树已有锁文件，确认锁文件、对应的既有依赖恢复命令和产物位置；按既有锁文件恢复本地依赖不等于变更依赖或锁文件。

这些事实应在连续卡的“范围”“本次一次性授权动作”或“满足条件后自动执行的动作”中写清。首次发现共享入口、相邻测试、必要的代码函数/文件迁移、既有锁文件的依赖恢复或本地验证产物时，只要仍在同一业务目标、语义授权边界和准确候选/worktree 内，就作为普通推进继续；发现实际需要改变业务目标、排除项、依赖版本或锁文件、候选/worktree 本身或外部边界时，才交回主任务。
