# 专项 Skill 选择

`dev-team` 始终保留任务目标、授权、候选、唯一写入者、质量、验收和 Git 决策。专项 Skill 只提供当前阶段需要的专业方法，不成为第二个协调中心，也不产生新的权限。

## 选择门禁

1. 先确定当前阶段：需求澄清、规划、实现、故障诊断、验收或收口。
2. 任务清楚且现有源码、配置、脚本和测试信号足够时，不使用额外 Skill。机械小修不因安装了更多 Skill 而升级流程。
3. 每个阶段最多选择一个主要专项 Skill。只有它明确要求共享词汇或底层参考时，才加载辅助 Skill。
4. 选择前确认该 Skill 当前可用、调用方式和副作用。不可用时报告并使用最小合格替代，不安装、不启用、不复制其完整流程。
5. Skill 若设置为仅用户调用，给出可复制的 `$skill-name` 命令并停止该分支；不得自动调用或模拟其工作流。
6. 记录完成条件。专项结果达到条件后回到任务协调员，由主任务检查实际成果和下一阶段。

实现和验收阶段同时读取 `dispatch-packet.md` 的“交付证据”；专项 Skill 的返回只有落入同一份 `delivery_evidence`，并由对应角色实际运行后才构成证据。不要另建第二套 TDD、诊断或评审记录。

## 可按任务自动选择

### 故障诊断门槛

根因未知或原始故障假设首次被证伪时，先进入故障诊断，使用当前可用的 `diagnosing-bugs` 方法。普通命令、语法或环境错误先核对对应工具，不冒充原始故障修复失败。可复现 Bug 尚无原始信号时不得派生产修复；v5 偶发故障可以先完成精确范围的日志/追踪和可诊断性交付，按 [recovery.md](recovery.md) 保留未验证边界。

故障诊断只使用 `diagnosing-bugs` 的阶段 1–4：建立并缩小稳定红灯、提出可证伪假设、以证据区分假设。生产修复的完成条件是：稳定红灯已实际运行且捕获原始症状、最小复现或根因证据已记录、正确回归接缝明确。偶发故障的可诊断性结果按 bug-diagnosis 返回，不能代替这些修复条件。主任务随后另行派发生产修复；该独立阶段可选择 `tdd`。阶段 5 只能在这个后续生产修复派单中使用，且派单已满足上述完成条件和写入授权。

故障身份、诊断工具写入、失败次数、第三次熔断和恢复目标的限制以 [recovery.md](recovery.md) 为准；不要在此处复制。

| 当前情况 | 主要专项 Skill | 使用边界 | 完成后回到主任务的条件 |
| --- | --- | --- | --- |
| 用户要求 test-first，或新行为存在值得验证的正确测试接缝 | `tdd` | 先证明测试能因目标行为变红；纯视觉问题不用源码文字匹配冒充行为测试 | 同一测试红转绿，目标行为复验通过 |
| 已进入故障诊断阶段 | `diagnosing-bugs` | 严格停在阶段 1–4；生产修复另行派单 | 满足故障诊断门槛的完成条件 |
| 视觉、布局、交互、响应式或组件状态 | `finesse-ui` | 本阶段唯一视觉权威；精确照图才改用 `product-design:image-to-code` | Design Read 已确认，实现和真实浏览器自检完成 |
| UI、状态模型或流程必须做出来才能决定 | `prototype` | 只回答一个设计问题，原型不是生产候选 | 问题得到明确答案，结论已带回正式任务 |
| 模块接口、职责或测试接缝不清 | `codebase-design` | 设计当前模块边界，不自动扫描或重构全项目 | 接口、职责、接缝和取舍已明确 |
| 业务术语混乱或需要记录 ADR | `domain-modeling` | 仅在领域模型发生变化时使用；普通读取术语不触发 | 术语和决定已写入项目规定位置 |
| 权限、认证、输入、敏感数据、支付或生产安全 | `ecc-security-review` | 进入严格路径；测试通过不能替代独立安全判断 | 风险、回滚边界和独立验收明确 |
| 已处于 merge 或 rebase 冲突 | `resolving-merge-conflicts` | 先核对两边意图和当前 Git 状态；不扩大为新功能 | 冲突完成、项目检查通过、剩余取舍已报告 |
| 需要当前互联网事实 | `agent-reach` | 只负责获取互联网材料，不替代产品决定或项目写入授权 | 来源与关键事实已返回 |
| 需要把一手资料沉淀为项目报告 | `research` | 只有用户授权项目文档写入时使用 | 带来源的报告已写入约定位置 |
| 只有人能完成第三方后台、凭证或切换步骤 | `wizard` | Agent 自己能做的步骤不生成向导；密钥和外部变更单独授权 | 人工步骤脚本和停止条件已交付 |
| 稳定的非机械 diff 有固定基线或规格 | `code-review` | 检查规范与需求两个维度；不能替代真实运行、UI、安全或外部状态验收 | 已处理确认问题或明确记录未解决项 |
| 候选准备合并、暂停、放弃或清理 | 不使用额外 Skill | 按 `git-lifecycle.md` 执行内部收口审计；当前授权必须逐项覆盖提交、推送、PR、合并或清理，未覆盖、失效、对象不一致或事实无法核验时停止受影响动作并交回主任务 | 成果去向、验证、引用和清理边界已确认 |

同一任务可以在不同阶段顺序使用不同 Skill，例如：根因未知的 Bug 先用 `diagnosing-bugs`，找到正确接缝后在新的实现阶段使用 `tdd`，稳定后再用 `code-review`。这不是同一阶段叠加多个流程。

## 只向用户推荐的 Matt Pocock Skill

以下 Skill 当前是仅用户调用，且会改变对话阶段、项目文档或问题跟踪系统。主任务只在条件成立时给出命令、说明影响并等待用户显式调用：

| 当前情况 | 给用户的命令 | 可能影响 |
| --- | --- | --- |
| 项目内需求不清，需要追问并记录术语和决定 | `$grill-with-docs 我想做……` | 可能更新 `CONTEXT.md` 和 ADR |
| 没有项目，只想把想法问清楚 | `$grill-me 我想做……` | 不修改项目 |
| 讨论已稳定，工作跨多个会话 | `$to-spec 把当前讨论整理成规格` | 写入已配置的问题跟踪系统 |
| 规格需要拆成可独立交付的任务 | `$to-tickets 把规格拆成任务` | 创建任务和依赖关系 |
| 超大工程，连决策路线都不清楚 | `$wayfinder 我们要……` | 创建决策地图和任务 |
| 外部 Issue 或 PR 需要分类、核实和补充说明 | `$triage 处理 Issue 或 PR` | 可能修改标签、评论或状态 |
| 关键知识只在其他人手里 | `$to-questionnaire 为……生成问卷` | 创建问卷文件 |
| 用户明确要求采用 Matt 的问题跟踪和领域文档体系 | `$setup-matt-pocock-skills` | 修改项目文档和 `docs/agents` 文档 |

运行 `to-spec`、`to-tickets`、`wayfinder` 或 `triage` 前，必须先确认项目已经显式完成对应设置；不能因为 Skill 已安装就自动改造仓库。

## 不接入自动开发流程

- `ask-matt` 本身也是路由器。不要在 `dev-team` 内再次调用它，避免两个协调中心互相改写流程。
- `implement` 与开发执行员职责重复，并包含自动提交行为。实现始终由 `dev-team` 选定的唯一写入者完成；提交仍按当前授权决定。
- `improve-codebase-architecture` 只在用户明确要求架构体检时推荐，不随普通功能自动扫描全项目。
- `handoff`、`teach` 和 `wait-what` 是会话或沟通工具，不属于开发阶段路由。
- 不自动安装、启用、禁用或更新任何 Skill，也不自动运行 `setup-matt-pocock-skills`。
